# 認証仕様（v2.0.0以降）

[最優先のコンセプト](../../README.md#最優先のコンセプト)を維持し、Go SSR・SQLite・同梱JavaScriptで実装する。外部認証サービス／CDNへの実行時接続は不要。WebAuthnの検証はGoライブラリで行い、独自に署名検証方式を実装しない。

現行v2.1.3には、v2.1.0の認証鮮度制限とv2.1.1の操作単位の本人確認をともに適用する。ログインから10分以内という条件だけでは、通常の保護操作は許可しない。

## ロールと通常ログイン

| ロール | 許可する方式 |
|---|---|
| User | 端末固定型パスキーのみ |
| Group Admin | 端末固定型パスキーのみ。管理委譲機能は引き続き未実装 |
| Portal Admin | 端末固定型パスキー、またはパスワード＋TOTP |

パスキーにはPINまたは生体認証による本人確認を必須とする。管理者がパスキーを選んだ場合、TOTPを追加要求しない。一般ユーザーが既存password／TOTPを保持していても通常ログインを許可しない。ラボ用MFA迂回は提供しない。DCVワンタイム認証・Proxy／Git専用トークンはWebログインとは別用途で、従来の認可境界を維持する。

認証JSON POSTは固定Originと一致する要求だけを受け付ける。管理者のコード発行／リセット／ユーザー作成と本人の削除フォームにはセッションに結び付けたCSRF tokenを付ける。`Referrer-Policy=no-referrer`を維持し、native formのOriginがnullでもCSRF tokenなしの操作を拒否する。

## パスキー検証

- `AWSPORTAL_WEBAUTHN_ORIGIN`に外部HTTPS Originを明示する。RP IDはそのDNSホスト名。パス・認証情報・クエリ・フラグメント・IPアドレスは不可。未設定／不正設定は起動時に拒否する。HTTP localhostは開発・自動試験専用。
- WebAuthnのchallenge、Origin、RP ID、署名、credential所有者、UP／UV、sign counterを検証する。`userVerification=required`とし、本人確認なしの応答を拒否する。
- 登録画面はplatform authenticatorを要求する。検証済み応答のBE（バックアップ可能）またはBS（バックアップ済み）が立つ鍵を登録・認証とも拒否する。クライアント画面の自己申告だけで同期禁止を判定しない。
- BE／BSは準拠する認証器の申告を署名検証した結果であり、配布PCの資産識別やTPMのハードウェア証明ではない。配布PCの管理・信頼済みCA・同期禁止設定は組織の端末管理で維持する。
- SQLiteには公開鍵・credential ID・counter・PC名を保存する。秘密鍵とPIN／生体情報はPortalへ送信・保存しない。1ユーザー最大10個、PC名は1〜80文字で重複不可。
- challengeは2分有効、HttpOnly・SameSite=Strict Cookieでブラウザーへ結び付け、完了時に1回だけ消費する。期限切れ・用途違い・再利用・リセット前のchallengeを拒否する。期限切れを掃除し、同時未完了はユーザー16件／全体4096件に制限する。

## 登録と復旧

管理者の本人確認後、30分有効・使い捨ての登録コードを発行する。DBへはSHA-256だけを保存する。コードは新規ログイン権限を与えず、登録成功でもセッションを作らない。登録後は新しい鍵でログインする。コードの消費・鍵保存・監査を同一トランザクションで確定する。コード再発行で旧コードと未完了登録を失効させる。

自分のPCへの追加登録・鍵削除、管理者のコード発行・リセットは、直近のログインまたは本人確認から10分以内の認証鮮度に加え、操作別の本人確認結果を必要とする。確認結果は同じセッション・同じ操作に結び付く2分有効・1回限りのもので、新しい鍵の追加では登録開始時に消費する。別PCへの登録は管理者から追加登録コードを受け取る。コードによる初回登録には既存ログインセッションを要求しない。最後の鍵を本人が削除することは許可せず、管理者のリセット経路を使用する。

管理者リセットは全鍵・未完了challenge・未使用DCV tokenを削除し、アカウントの認証世代を更新する。旧Portalセッションは次の要求で拒否する。既存DCVセッションのOS側終了は行わない。ロック解除、再有効化は独立操作で、リセットや登録で迂回できない。全Portal Adminの復旧には停止中のローカル管理CLIを使用する。

## アカウント状態と監査

ログイン／登録開始／完了で有効状態・30日未アクセス期限・最終ロック・待ち時間を確認し、完了トランザクションでも再確認する。パスキー認証失敗・登録コードの誤り・管理者password／TOTPの誤りは同じ失敗回数に合算する。4〜9回の待ち時間と10回ロックは[復旧手順](../operations/password-recovery.md)に従う。キャンセル、期限切れchallenge、DBエラーは誤入力として加算しない。

`passkey.invite`／`passkey.reset`／`passkey.register`／`passkey.delete`とloginを監査する。成功した管理操作・登録・パスキーログインはDB更新と監査を同時に確定する。コード・credential応答・秘密鍵・Cookie・PIN・password・TOTPコードを監査へ記録しない。管理者のpassword変更強制とBreak-glass後の変更は継続する。

## 配布・受入

更新は[現行リリース手順](../releases/v2.1.3.md#更新受入)に従い、旧版からの移行は該当する過去版の手順も確認する。署名付き認証応答、UV／同期禁止、再利用拒否、復旧と状態競合、仮想認証器によるChromium画面操作を自動検証する。対象の配布PC・OS・ブラウザー・社内CA・実t4g.microでの受入は本番適用前に別途行う。

## v2.1.0の追加防御

Cookie認証の全更新操作でCSRF tokenとOrigin／Fetch Metadataを共通検証する。v2.1.0で導入した10分以内の認証鮮度制限は維持し、現在は次節の操作単位の本人確認も併用する。本人確認成功で認証鮮度を更新する。Portal Adminのpassword＋TOTPとパスキーの両方式を維持し、TOTPの検証済み時間ステップはログイン更新と同じDBトランザクションで1回だけ消費する。

認証開始は送信元別の回数と全体同時実行数を制限する。未完了ログインチャレンジの枠を使い切っても古いloginを入れ替え、正規の開始要求を拒否し続けない。登録用challengeをlogin開始で追い出すことはない。単一ユーザーの上限16／全体4096と2分の期限を維持する。

ロック／無効化／復旧／password変更で認証世代と専用tokenを失効させ、解除後にも旧tokenを復活させない。Cookieセッションは絶対8時間・無操作30分、1ユーザー5件／全体4096件。DBのTOTP秘密はAES-256-GCMで暗号化し、鍵は別ファイルで保管する。[移行手順](../releases/v2.1.0.md)を参照する。

## v2.1.1の操作単位の本人確認

新規パスキーの追加・削除、登録コード発行／リセット、管理者のMFA・password変更と管理操作は、ログイン時刻だけを根拠にしない。登録済みパスキー、またはPortal Adminの現在のpassword＋TOTPで改めて確認する。確認結果はセッションと操作経路に結び付け、2分有効・1回限りとし、同時要求でも1回だけ消費する。別の操作・Cookie・期限切れ・リセット後の確認結果を拒否する。確認結果そのものをURL・監査へ記録しない。

既存のパスキーを持たない初回登録は、本人確認済み管理者が発行する使い捨て登録コードの経路を使用する。break-glass等の強制password変更はpassword＋TOTPによる初回ログインから2分以内の限定操作とし、他の管理操作へ流用しない。

Cookie認証の更新は監査intentを保存してから実行する。DB内の認証情報変更は監査と原子的に確定し、外部操作の結果が保存できなかった場合は未完了intentと独立した標準ログ警告で照合する。[更新・監査障害時の手順](../releases/v2.1.1.md)を参照する。
