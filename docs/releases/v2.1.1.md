# v2.1.1

## 変更

- パスキーの追加・削除、管理者の認証情報変更と管理操作に、登録済みパスキーまたは管理者の現在のpassword＋TOTPによる操作単位の本人確認を追加する。ログイン直後でもCookieだけの操作を許可しない。確認結果はセッション・操作経路に結び付け、2分以内・1回限りで消費する。新しいパスキーの登録は開始時に確認結果を消費し、登録challengeを同じセッションに結び付ける。
- 一般利用者の通常ログイン・初回の登録コードによるパスキー登録を維持する。確認時のパスキーは既存鍵のUV・署名・Origin・counterを検証し、管理者TOTPも使用済み時間ステップを原子的に消費する。
- Mirrorの管理者向け設定・割り当て・専用token発行／失効にも本人確認と認証鮮度の制限を適用する。一般利用者の許可された同期操作は従来のACLを維持する。
- Cookie認証の更新要求は処理前に監査intentを永続化し、保存できなければ503で拒否する。処理後の結果保存に失敗した場合は未完了intentを残し、標準ログへSECURITY警告を出す。既に完了した操作を再実行させる応答には変更しない。
- password変更、TOTP端末の追加・削除、DCVワンタイム認証は監査と同じDBトランザクションで確定する。監査のINSERT失敗時は状態変更をロールバックする。一般Auditの保存errorを返し、DBとは独立した標準ログへ通知する。
- 予約EC2操作とMirror workerも監査intentを保存してから外部処理を実行する。Proxyは接続開始前の監査保存を必須とする。
- Cookie認証の本文上限128 KiBをCSRF tokenの取得方法にかかわらず適用する。新しい同梱JavaScriptのURLを更新し、旧キャッシュによる本人確認失敗を避ける。
- コミット前フックからGit統合テストへリポジトリ固有の環境変数を渡さず、テスト用リポジトリの初期化が作業ブランチを変更しないようにする。

## 更新・受入

1. Portalを停止し、DB・設定・TOTP暗号鍵をバックアップする。2.1.0の暗号鍵を維持し、DBと鍵の保管先を分ける。旧版からの暗号化移行は[v2.1.0](v2.1.0.md)の手順を先に確認する。
2. 同じv2.1.1タグのPortal・管理CLI・同梱ファイルを配置する。起動時に監査操作の追跡テーブルを追加する。起動前のDBバックアップを切り戻し用に保持する。
3. ブラウザーを再読込する。保護された操作で本人確認画面が表示されたら、既存の認証要素で確認し、戻った画面でもう一度操作する。passwordや操作フォームの入力値は自動再送しない。TOTPは直前に使ったコードの次のコードを使用する。
4. 管理者の両認証方式、一般利用者のパスキー、追加・削除、Mirror管理と一般同期、監査保存障害時の拒否を受入確認する。ブラウザーには1操作分の短命な確認結果だけを保存し、URLや監査ログには記録しない。
5. 標準ログの`SECURITY audit persistence failed`を中央ログの通知対象にする。`audit_operations`に`completed IS NULL`の行が残る場合は、対応する監査intentとAWS/OS等の実状態を照合し、外部操作を重複実行しない。応答完了後の監査保存失敗では自動的な成功／失敗の確定は行わない。

break-glass後などのpassword＋TOTPによる初回ログインでは、強制password変更だけを2分以内に許可する。その他の操作は行えず、変更後はセッション・専用tokenを失効させる。2分を過ぎた場合は本人確認を行う。この限定された初回変更を通常の認証情報変更へ流用しない。

## 検証

Cookieだけの新鍵登録拒否、登録済み鍵・password＋TOTPでの本人確認、確認結果の期限・用途・セッション結合・同時再利用拒否、Mirror管理の保護、監査障害でのDBロールバックと外部処理拒否、結果保存失敗時の未完了intentを回帰試験する。同梱UIの本人確認と登録・削除、htmx管理操作、既存の必須試験、ARM64ビルド、govulncheckを確認する。実AWS/DCV・配布端末の受入は適用環境で実施する。
