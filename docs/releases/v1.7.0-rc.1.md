# v1.7.0-rc.1 — 固定Shared基盤とJob/cgroup計測の候補版

本版は二段階実装仕様書の第1段階を進める**事前検証用候補版**。第1段階の完了版・本番受入済み版ではない。自動増設・自動終了は有効化できない。AWSへ自動デプロイする変更は含まない。

## 変更

- PR #38の固定Shared予約、本人EFS準備、native DCV、切断保持、明示解放、S3永続queue、オプトインIaCを含む。
- `awsportal-job COMMAND [ARG ...]` がsystemd user scope内からroot AgentへJobを登録する。Unix socketのSO_PEERCREDで取得した実PID/UIDと `/proc/<PID>/cgroup` を確認する。ユーザーが渡すUID・counter・任意コマンドをrootで実行しない。
- CPUAccounting/MemoryAccounting/IOAccountingを指定し、cgroup v2の `cpu.stat`、`memory.current`、`io.stat`、`cgroup.events` をrootで読む。複数block deviceのread/write bytesを合算し、scope配下の子cgroupも対象にする。CPUはmicroseconds、メモリは最新bytes、I/Oは累積bytes。
- 開始/コマンド終了をroot保護の `jobs.json` に保存する。30秒pollより短いJobも記録する。コマンド終了後もscopeに子プロセスがあればRUNNINGを維持する。非登録作業も既存 `/proc` 保護を継承する。
- Agent restartでledgerを復元する。OS boot変更はINTERRUPTEDとして記録し成功とはしない。Portalへのheartbeat成功後にだけ終端Jobをローカルledgerから削除する。
- SQLite migration 2でmanaged_jobs/job_samplesを追加する。既存Agent v2の報告は互換受理し、`measurement_version=1` を追加する。既知の実行中Jobが報告から消えた場合は報告を拒否し、席を解放しない。
- boot/sequence再送の同一性を維持する。新規Jobは当該instance/generationの有効Assignmentへ限定する。Job IDのOwner/boot/start時刻変更、終端状態の変更は拒否する。すべての更新はheartbeatと同じtransactionで行う。
- 原始Job計測をusage/v2のS3 queueへ含める。cgroup epoch変更・counter減少・欠測はusage差分に変換しない。job_samplesの差分はNULLと品質理由で保存する。
- Environmentsは本人のJob履歴、Environment Adminは全体の直近100件を表示する。Group ACLだけで他人のJob履歴を読めない。90秒超の実行中Jobは「計測が古い」と表示する。
- リリースはVERSIONの明示変更時に起動する。候補版はGitHub prereleaseとして配布し、既公開tagと異なるcommitでの上書きを拒否する。archiveに新しいjob_metrics.pyを含め、公開後にchecksum・7ファイルの内容・tag commitを確認する。

## 品質と制限

|品質|意味|
|---|---|
|ok|counter読取成功。期間CPU課金や完全性証明を意味しない|
|baseline|DBの初回sample。差分はNULL|
|counter_reset|epoch変更または累積値減少。差分はNULL|
|gap|sample時刻の非前進または90秒超の欠測。差分はNULL|
|unavailable|counter読取不能。UNKNOWNのJobを保持|
|scope_removed|scope消失後に終了判定。終了瞬間のcounterは不完全な可能性があり、最後の読取値を保存|
|boot_changed|OS再起動でJob中断。最後の読取値を保存|

Linux cgroup v2とsystemd user manager、CPU/Memory/I/O controllerが必要。controller未提供時は登録/計測を失敗させ、ゼロ使用とみなさない。EFS/NFSの全I/Oはblock deviceのio.statでは測れない。Memoryはgaugeであり時間積分・請求には使わない。scope削除直前の未観測I/O・CPUを推定で補完しない。raw値は観測用であり費用配賦は未提供。

ローカルledgerは実行中＋未送信終端Job最大128件。Portal不通で上限に達したら新規wrapper起動を拒否する。コマンドは実行しない。Job command line・環境変数・資格情報はledgerへ記録しない。SQLite履歴の圧縮/保持期限・Parquetは後続変更。

## 導入・復旧

1. 既存Portalを停止しDB/WALの整合backupを取得する。複製DBでmigrationとlogin/MFA/既存Personal/DCV/mirrorを確認する。詳細は [固定pilot導入手順](../archive/shared-pilot.md)。
2. Portal/AdminのARM64 binaryを候補版から更新する。既存AgentのままではJob計測は提供しない。
3. SharedのJob/desktopを保存・終了して保守時間を確保する。候補版のdcvディレクトリ一式で `sudo bash dcv/install.sh` を実行する。agent.py単独コピーではjob_metrics.pyが不足する。
4. Agentの既存stateを保持しサービスを再起動する。jobs.jsonを初期化/削除して実行中Jobを消さない。AMIにはmachine credentialやledgerを焼き込まない。
5. 2人pilotでラッパー、sleep/I/O、Jupyter、切断、子プロセス、Agent/Portal再起動、HOME分離を実機検証する。失敗時は新規受付を止め既存Job/HOMEを保持する。

既存ラボの既定配布版は安定版v1.6.0のまま。候補版を明示して別の使い捨てラボを作る場合：

```bash
BINARY_URL='https://github.com/sptree-m/awsportal/releases/download/v1.7.0-rc.1/awsportal-v1.7.0-rc.1-linux-arm64.tar.gz' bash lab/create.sh
```

このコマンドはAWSリソースを作る。検証用AWSアカウント・承認済み接続CIDRを設定して実施する。Shared EFS/pilotの構築・受入を自動で完了させるものではない。backup互換を確認せず旧binaryへdowngradeしない。

## 自動検証と残項目

Go race全回帰、ledger重複再送/Owner/Assignment境界/counter reset/欠測/履歴・S3 queue、HTTP本人/管理者画面、Python短いJob/子プロセス/peer UID/cgroup境界/boot変更/登録失敗時未実行を検証する。ブラウザでは本人境界とJob画面を4デスクトップ解像度＋390pxで検証する。Terraform・セキュリティ・既存DCV/ラボのCIも実行する。

AWS実機のcgroup・EFS/DCV・通信分離と2ユーザー5営業日pilotは未実施。Personal EFS移行、Group EFS、Dataset cache/manifest、scratch quota、Storage counters、Parquet/保持、CUR保存は後続変更。第2段階の増減・請求照合・Windows Box Importも未実装。S1受入が揃うまでは正式な第1段階完了リリースとして扱わない。

参照：Linux kernel [cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)。
