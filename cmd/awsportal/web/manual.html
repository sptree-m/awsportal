パスキー登録・ログイン

一般User／Group Adminの通常ログインは、この配布PCのPIN・指紋・顔認証によるパスキーだけです。クラウド同期のパスキーは使用できません。信頼済みHTTPSと指定ホスト名で接続してください。

  1. 初回は管理者からユーザー名と30分有効の登録コードを受け取ります。
  2. ログイン画面の「初回登録・管理者による再登録」でユーザー名・コード・PC名を入力し、このPCに登録します。
  3. 登録後はログイン画面へ戻り「パスキーでログイン」を押します。登録だけではログインになりません。

最大10台分を登録できます。別PC用には管理者へ追加登録コードを依頼してください。紛失・交換時は管理者へリセットを依頼し、必要なPCに再登録します。「パスキー」でPC名を確認できます。ログイン後10分以内なら追加登録・不要キー削除が可能です。削除後はログインし直してください。

01 / NETWORK

プロキシの設定方法

許可された外部サイトへは、管理者が用意したHTTPSプロキシを経由します。Portalのパスキーや管理者password・TOTPコードをツールへ保存する必要はありません。

  1. 管理者からプロキシ接続先、社内CA証明書、プロキシ用ユーザー名と専用トークンを受け取ります。専用トークンは1〜90日で失効します。
  2. HTTPSプロキシ対応のcurlを準備します。接続先のCAとプロキシのCAを信頼できるように設定します。
  3. 下記のコマンドで、管理者が許可した接続先への通信を確認します。トークン入力は画面に表示されません。

接続先：{{.ProxyExampleURL}}{{if not .ProxyConfigured}} （例示です。管理者に確認した値へ置き換えてください。）{{end}}

PROXY_URL='{{.ProxyExampleURL}}'
read -r -p 'Proxy user: ' PROXY_USER
read -r -s -p 'Proxy token: ' PROXY_TOKEN; echo
read -r -p '許可された接続先URL: ' TARGET_URL
printf 'proxy-user = "%s:%s"\n' "$PROXY_USER" "$PROXY_TOKEN" |
  curl --config - --proxy "$PROXY_URL" --max-time 20 "$TARGET_URL"
unset PROXY_USER PROXY_TOKEN

社内CAをOSの信頼ストアに登録していない場合、curlに --proxy-cacert /path/to/proxy-ca.pem を追加します。接続先も社内CAを使う場合は --cacert /path/to/target-ca.pem を追加します。

他のツールや自動タスクで使う場合

対応ツールでは HTTP_PROXY / HTTPS_PROXY に上記プロキシ接続先を指定します。変数名HTTPS_PROXYは「HTTPS宛て通信のプロキシ」を意味します。実際の接続先もHTTPS方式のプロキシであることを確認してください。

認証情報の設定方法はツールごとに異なります。専用トークンは権限0600の設定ファイルなどで保護し、URL・コマンド引数・共有ログへ記載しないでください。HTTPSプロキシに対応しないツールは、この方法では利用できません。

HTTPS通信は接続先ホストとポートで許可されます。HTTPS内部のGET/POSTなどを区別する仕組みではありません。GitLabの読み取り専用運用には下のGitミラーを使います。

02 / SOURCE CODE

Gitミラーの利用方法

ポータルが社内GitLabからコードを取得します。利用者EC2はポータル内のミラーからclone/fetchします。GitLabの資格情報をEC2へ配布せず、ミラーへのpushを拒否します。

  1. Git Mirrors画面で割り当て済みのリポジトリIDを確認します。同期要求をするには「読み取り＋同期要求」の権限が必要です。
  2. 管理者からポータルの専用ミラートークンと社内CAを受け取ります。プロキシのトークンやPortalのパスワードとは別です。
  3. EC2にPython3、Git、Git LFSを準備し、クライアントをポータルからダウンロードします。

接続先：{{.PortalExampleURL}}{{if not .PortalConfigured}} （例示です。管理者に確認した値へ置き換えてください。）{{end}}

同期クライアントをダウンロード

1. EC2へクライアントを配置 
PORTAL_URL='{{.PortalExampleURL}}'
mkdir -p "$HOME/.local/bin"
curl --fail --silent --show-error \
  "$PORTAL_URL/static/web/awsportal-mirror.py" \
  -o "$HOME/.local/bin/awsportal-mirror"
chmod 755 "$HOME/.local/bin/awsportal-mirror"
export PATH="$HOME/.local/bin:$PATH"

社内CAをOSの信頼ストアに登録していない場合は、curlに --cacert /path/to/portal-ca.pem を追加してください。プロキシ経由ではなく、ポータルへ直接届く経路が必要です。

2. トークンを安全に設定

次のPythonコマンドはトークンを非表示で読み取り、通常ファイルを権限0600で新規作成します。既存ファイルは上書きしません。CAをOSで信頼済みの場合、CAファイルの入力は空欄にできます。

python3 -c '
import getpass, json, os
from pathlib import Path
p = Path.home() / ".config/awsportal/mirror.json"
p.parent.mkdir(parents=True, exist_ok=True, mode=0o700)
config = {
    "portal_url": "{{.PortalExampleURL}}",
    "token": getpass.getpass("Mirror token: "),
}
ca = input("Portal CA file (空欄可): ").strip()
if ca:
    config["ca_file"] = ca
fd = os.open(p, os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
with os.fdopen(fd, "w") as f:
    json.dump(config, f)
print("設定ファイルを作成しました")
'
3. 同期してコードを取得

下記の 1 を割り当て済みリポジトリIDへ置き換えます。main は実際のブランチ名に合わせてください。

# GitLab→ポータルの同期。成功まで待ち、失敗時はエラー終了
awsportal-mirror sync 1 --wait

# 初回取得
awsportal-mirror clone 1 ./source

# 取得済みのリポジトリを更新
awsportal-mirror fetch 1 ./source
git -C ./source merge --ff-only origin/main
git -C ./source lfs checkout

読み取りのみの場合、sync は使えません。管理者の定期同期・初回同期が完了したミラーからclone/fetchしてください。fetchだけでは作業ツリーは変更されません。

自動タスクの実行例 
set -eu
awsportal-mirror sync 1 --wait
if [ ! -d ./source/.git ]; then
  awsportal-mirror clone 1 ./source
else
  awsportal-mirror fetch 1 ./source
  git -C ./source merge --ff-only origin/main
  git -C ./source lfs checkout
fi
# 同期・更新が成功した場合だけ、ここでビルドやタスクを実行

既定の待機は最大900秒。タイムアウトや同期失敗は終了コード1です。awsportal-mirror status JOB_ID で後から状態を確認できます。専用トークンの期限は更新されないため、定期的な交換が必要です。

LFSファイルもポータルから取得します。Git LFSをインストールしてから同梱クライアントを使ってください。cloneは実体を展開し、fetchはLFSをキャッシュします。merge後に git lfs checkout で実体を展開します。LFS uploadは拒否されます。

GitLab API・添付ファイル・CI artifact、サブモジュールの自動再帰取得は未対応です。

03 / HELP

困ったとき

接続できない・タイムアウト
接続先、DNS、社内CA、EC2からの通信許可を管理者へ確認してください。GitミラーはポータルHTTPSへ直接接続します。SGやプロキシ許可を利用者が変更する必要はありません。
証明書エラー
指定されたCAファイルと接続先名を確認してください。TLS検証を無効化して回避しないでください。
プロキシの407 / 403
407は認証情報・トークン期限・アカウントの状態、403は接続先・ポート・許可設定を確認します。アカウント維持のため定期的なPortalログインも必要です。
ミラーの401 / 403
専用ミラートークンの期限、アカウント、リポジトリ割り当て、読み取り／同期要求の権限を確認してください。
ミラーの409 / 503
409は初回同期が未完了、503はミラー機能の準備状況を管理者へ確認してください。pushなどの書き込み要求は403で拒否されます。
同期の429 / error
429は短時間の再要求です。sync --wait は期限内で自動再試行します。errorの場合はジョブIDを管理者へ連絡してください。前回成功したコードは残ります。
コードの更新に失敗
ブランチ名、originのミラーURL、作業ツリーの変更を確認してください。クライアントはファイルを強制上書きしません。

ADMIN / CERTIFICATES & HOSTS

証明書生成と64 IPのhosts配布

利用者への公開CA・hosts登録スクリプトの配布場所はログイン画面です。この管理者手順と支援ツールで配布物を準備します。64個のIPに対応するホスト名を台帳へ登録し、追加の別名を含め最大128件まで扱えます。

管理者用の生成支援ツールをダウンロード

1. ホスト名・IPとCAを準備する

Python 3とOpenSSLを備えた管理者専用Linux/macOS環境で実行します。社内の管理ドメイン配下でPortal、Proxy、DCV等の名前を固定し、実際に利用する64 IPと対応付けます。IPの連番やCIDRから未承認の接続先を自動追加しません。hosts.jsonは次の形式で全接続先を記載します。名前は重複不可、同じIPの別名は登録可能です。

{"hosts":[
  {"name":"portal.company.example","ip":"192.0.2.10"},
  {"name":"dcv01.company.example","ip":"192.0.2.11"}
]}

例示の値は実ホスト名・IPに置き換えてください。社内CAがある場合はその発行手順を使います。独立した検証用CAを作る場合は管理者専用ディレクトリで次を実行し、CA秘密鍵を発行環境に保持します。

umask 077
openssl req -x509 -newkey rsa:3072 -nodes -sha256 -days 3650 \
  -keyout ca.key -out ca.crt -subj '/CN=awsportal local CA' \
  -addext 'basicConstraints=critical,CA:TRUE' \
  -addext 'keyUsage=critical,keyCertSign,cRLSign'
2. hosts設定・CSR・サーバー証明書を生成する

社内PKIへ申請する場合はCSR生成を使います。ツールはhosts台帳を検証し、ホストごとのRSA秘密鍵とDNS SAN付きCSR、署名用拡張設定を作ります。社内CAへserver.csrを申請し、同じDNS SAN・serverAuth付きの証明書を取得します。

python3 generate-preparation.py --hosts hosts.json --out generated-csr

ローカル発行用CAの利用が許可されている場合は署名まで一括実行できます。CAは365日以上有効なものが必要です。暗号化CA鍵のパスフレーズはOpenSSLの対話入力を使い、コマンドや台帳には記載しません。

python3 generate-preparation.py --hosts hosts.json --out generated \
  --ca-cert /secure/ca.crt --ca-key /secure/ca.key

出力はhosts.jsonと、ホスト名ごとのserver.key・server.csr・server.ext・署名時のserver.crtです。証明書は365日、ホストごとに別鍵・別シリアル番号です。既存出力は上書きしません。途中失敗時は管理者が出力を確認し、新しい出力先で再実行します。サーバー証明書・秘密鍵を対象のHTTPS終端やDCVへ個別配置し、Go HTTPSの場合はPortalを再起動し、リバースプロキシやDCVの場合は構文確認・reloadと接続を検証してください。ツールはサーバー設定やAWSを変更しません。

PortalのHTTPS待受を設定する

既定はGo単体のHTTPSです。Portal用のSAN付きサーバー証明書と秘密鍵をTLS専用ディレクトリへ置き、service userだけが秘密鍵を読める権限にします。公開CAの配布設定とは別です。次のsystemd設定では非特権userによる443待受にcapabilityを使います。

[Service]
Environment=AWSPORTAL_HTTP_MODE=https
Environment=AWSPORTAL_ADDR=:443
Environment=AWSPORTAL_TLS_CERT=/etc/awsportal/tls/portal.crt
Environment=AWSPORTAL_TLS_KEY=/etc/awsportal/tls/portal.key
AmbientCapabilities=CAP_NET_BIND_SERVICE
CapabilityBoundingSet=CAP_NET_BIND_SERVICE

AWSPORTAL_WEBAUTHN_ORIGINはブラウザーで使う固定HTTPS Originに合わせます。高位ポートならcapabilityは不要で、Originにもポートを含めます。TLS 1.2以上を使用し、証明書・鍵の不備は起動エラーになります。HTTPへの自動切替はありません。証明書更新後はPortalを再起動してください。

HTTPSリバースプロキシを使う場合はAWSPORTAL_HTTP_MODE=http、AWSPORTAL_ADDR=127.0.0.1:8080を設定し、AWSPORTAL_TLS_CERTとAWSPORTAL_TLS_KEYを解除します。外部HTTPS OriginとセキュアCookieは維持し、リバースプロキシへサーバー証明書・鍵を設定します。既存のHTTP構成から更新する場合もHTTPモードの明示設定が必要です。

3. ログイン画面へ配布を設定する
  1. Portalホストの /etc/awsportal/client-preparation/ に、公開CAの ca.crt と生成済み hosts.json だけを配置します。生成ディレクトリ全体や秘密鍵をアップロードしないでください。
  2. Portalのsystemd設定で次の2変数を指定し、設定変更後にdaemon-reloadとPortal再起動を行います。
Environment=AWSPORTAL_PREPARATION_CA_FILE=/etc/awsportal/client-preparation/ca.crt
Environment=AWSPORTAL_PREPARATION_HOSTS_FILE=/etc/awsportal/client-preparation/hosts.json

ログイン画面の「事前準備：証明書・hosts設定」から公開CAと端末準備ZIPを配布します。ZIPには公開CA、全件のhosts対応表、WindowsとmacOS/Linuxの適用スクリプトが入ります。生成ツールや秘密鍵は含めません。CAフィンガープリントは別の管理経路でも通知します。

初回端末がPortalの名前解決・CA信頼をまだ持たない場合は、既存の信頼済み社内配布経路で同じZIPを渡します。端末側は既定プレビューで確認し、管理者権限で適用してからブラウザーを再起動します。ブラウザーだけでhosts・信頼ストアを変更することはできません。

4. 更新・復旧とパスキー

IP変更時は同じ台帳を更新し、Portalを再起動して新しいZIPをログイン画面で配布します。端末で再適用すると指定した名前を更新し、他のhosts別名を保持してバックアップを作ります。台帳から削除した名前は自動削除されないため、管理者がバックアップと管理対象を照合して削除します。

サーバー証明書の更新は同じ名前で新しい出力先を生成して再配置します。同じCAでの更新なら通常は端末のCA再登録は不要です。CA交代時は新CAを端末へ先行配布し、移行後に旧CAをフィンガープリントで特定して削除します。現行配布設定はCA1枚です。

v2.0.0ではPortalのHTTPSホスト名を固定し、起動設定AWSPORTAL_WEBAUTHN_ORIGINをそのOriginへ合わせます。RP IDはPortalのホスト名です。64件すべてを認証元にする必要はありません。証明書・hosts設定後、本人確認した利用者へ登録コードを発行し、各PCでパスキーを登録します。

詳細・初回導入：docs/deployment/setup.md、配布・端末適用・復旧：docs/operations/site-customization.md。

ADMIN / COMPUTE

管理者マニュアル：EC2作成と起動時の種類選択

登録済みEC2の起動・停止と、承認済み構成からのShared自動作成は実装済みです。任意Personal EC2の作成、利用者が起動ごとにインスタンスタイプを選ぶ画面、既存EC2の種類変更は未実装です。Golden AMIを登録しても、これらの機能は有効になりません。

ポータル外で作成して登録する
  1. 管理者用AWS CLIまたは組織のIaCで、検証済みAMIと承認済み起動テンプレートを用意します。Private Subnet、SG、IAM Role、ディスク、公開IPなし、IMDSv2を固定します。一般利用者へAWS資格情報は配布しません。
  2. 新規作成時に許可されたインスタンスタイプを指定します。x86_64用AMIではm7i/m7a/c7i/r7i、ARM64用AMIではm7gなど、同じアーキテクチャの検証済み候補から選びます。GPUは別途設計が必要です。
  3. 作成したEC2を、Portal停止中またはDB排他を確保した保守時間に管理CLIの add-instance で登録します。Instance AdminでDCVホストとEC2専用認証キー、利用者・グループ割り当てを設定します。
  4. EC2側へroot所有・0600のAgent設定を配置し、Agentを開始します。DCV設定版と適用版の一致、本人のネイティブ接続を確認します。作成だけでは自動登録・認証設定されません。Personal/EFSを使う場合はEnvironment AdminでOwner・ストレージとHOME leaseも設定します。

同じEC2を使い続ける場合は、停止を確認してから種類を変更し、再起動します。停止・起動だけでは種類もAMIも変わりません。毎回新規作成する場合は、保存データをEFS/S3へ分離し、ローカルディスクを削除する前に永続化とHOME解放を確認してください。

既存Shared自動作成を導入する
  1. Golden AMI、固定Shared pilot、User/Group EFS、Scratch、Agentと計測を準備し、固定pilotで実機受入を行います。
  2. 組織管理のTerraformで managed-profile とShared用 two-stage を構築します。現在のインスタンスタイプは起動テンプレートで固定です。Portalには承認WorkflowのStart/Describeだけを許可し、RunInstances/TerminateInstancesはworkerへ分離します。
  3. 下のAMI手順でNEXT登録とSTABLE昇格を行い、workerの承認設定を一致させます。AWSPORTAL_PROVISION_WORKFLOW / AWSPORTAL_TERMINATE_WORKFLOW に対象ARNを設定します。
  4. 2名・5営業日の観測記録と理由を 運用・費用・取り込み に保存し、poolの増設と AWSPORTAL_SCALE_OUT=true を有効化します。自動終了はdrain・HOME解放の実機確認後に、poolの終了と AWSPORTAL_TERMINATE=true を有効化します。

全体・poolとも既定OFFです。最大5台、1台2席。EC2がrunningになっただけでは準備完了になりません。Agent、DCV、HOME、計測の確認が必要です。将来タイプ選択を追加する際も、承認候補・利用者権限・上限をWorkflowとworkerで検査します。

ADMIN / GOLDEN AMI

Golden AMIの作成・配布・更新

AMIの製造と配布は管理者のAWS環境で実施します。ポータルは検証済みAMIの登録・昇格を管理し、AMI自体を作成しません。

1. ビルドして検証する
  1. 用途とCPUアーキテクチャごとにベースAMIを選び、AMI ID、OS、パッケージ、業務ソフト、Portalと同じreleaseのAgentを固定します。現行自動インストーラー dcv/install.sh はUbuntu 24.04のARM64/x86_64に対応しています。
  2. 専用構築EC2にDCV/XFCE、Agent、job broker、Storageと起動時初期化処理を配置します。EFS利用時は amazon-efs-utils も別途導入します。DCVポートと社内CAを本番構成に合わせます。
  3. 利用者データ、EC2専用認証キー、個人の資格情報を含めずAMIを作成します。動的SharedのUserDataには設定Parameter名だけを渡し、起動時にSSMから各EC2の認証情報を取得します。初回は専用構築EC2から手動作成し、再現手順をEC2 Image Builderのレシピとテストへ移せます。Image Builderのパイプラインは別途構築します。
  4. 新AMIから別のEC2を作成し、Agent登録、DCVネイティブ接続、DLP、EFS隔離、Scratch、job、再起動と安全な終了を実機確認します。ビルド定義・成果物一覧のSHA256と検証記録を保存します。
2. 配布して承認設定を揃える
  1. 同一account/RegionではAMI IDを使います。他Regionへはコピーし、他accountへは起動許可の共有またはコピーを行います。Image BuilderのDistribution settingsで自動化できます。暗号化AMIのaccount間共有にはカスタマー管理KMSキーと利用許可が必要です。既定のAWS管理キーでは共有できません。
  2. 配布先ごとのAMI ID・所有account・KMSキーを記録し、AMIへ awsportal:golden-sha256 タグを付けます。この値は検証成果物の証跡で、AMI全体についてAWSが返すチェックサムではありません。
  3. 配布先AMIを指定した起動テンプレートの数値バージョンを作り、Private Subnet/SG、IAM Profile、IMDSv2、暗号化EBSを確認します。動的Sharedのroot/scratchはDeleteOnTerminationとし、HOME/Group EFSは保持します。組織提供AMIは approved_ami_owners へ所有accountを指定します。
3. NEXTからSTABLEへ更新する
  1. Golden AMI管理画面でProfile、Golden version、配布先AMI ID、起動テンプレートID、数値バージョン、64桁SHA256、実機検証記録を入力し、NEXT登録します。
  2. 更新中は増設をOFFにし、送信済みWorkflowの完了・再照合を確認します。管理者がIaC側の approved_pools を同じAMI/LT/数値version/SHAへ更新し、昇格理由を記録してSTABLEへ進めます。不一致では新規作成が拒否されます。
  3. 新規作成を試験し、準備完了と接続を確認して増設を戻します。PortalとGolden AMIのAgentを互換性のある同じreleaseへ揃えます。稼働中・停止中の既存EC2は昇格だけでは置換されません。
  4. 不具合時は増設を止め、旧AMIの新しいGolden versionをNEXTへ登録し、承認設定を旧AMI/LT/SHAへ戻して再昇格します。ARCHIVEDから直接戻す操作はありません。既存EC2は保守時間に個別対応し、HOME/Group EFSは保持します。

旧AMI・スナップショットは復旧期間と参照中の起動テンプレートを確認してから整理します。停止中もEBS、保持したAMIのスナップショット、EFS等の費用は続きます。

同じreleaseのソース文書：docs/operations/instances.md、docs/operations/environments.md、docs/deployment/organization-network.md、docs/operations/dcv.md。構築手順・組織のIAM/ネットワーク設定と併せて確認してください。

DCVデスクトップ接続

EC2 Instancesの「接続」を押すと、割り当てられたEC2へポータル認証で接続できます。EC2用のパスワード入力は不要です。公式DCVネイティブクライアントを事前にインストールしてください。ブラウザでのDCVデスクトップ接続は禁止です。ポータル自体はブラウザで使用します。

あなたの専用OSユーザーとセッション名: {{.DCVOSUser}}。ホームはユーザーごとに分離されます。通常のポータル管理者もEC2のsudo権限は自動付与されません。

起動直後や割り当て直後は同期完了までお待ちください。割り当て解除やアカウント無効化後はセッションと実行中タスクが終了します。ホームデータは保持されます。
